# Lab3 设计者与验证者的两条思路

## 一、设计者：先有需求，再决定连接

### 1. 外部要完成什么

主机通过APB写入一帧报文、配置处理规则、发出START，之后读到busy/done、报文结果和IRQ。Lab1已经负责总线与存储，Lab2已经负责算法；本次不是再写一个算法核，而是让这三部分真正协同。

### 2. 哪些是输入、输出和需要保存的信息

ppa_top的输入端口是PCLK/PRESETn及APB请求；输出端口是APB响应和irq_o。配置仍由M1保存，报文仍由M2保存，处理进度与结果仍由M3保存。顶层不需要新的状态寄存器，因此没有新增always_ff或FSM。

### 3. 把需求整理为连线规则

| 需求 | 驱动者 | 接收者 | 为什么不能接错 |
| --- | --- | --- | --- |
| 软件写报文 | M1的we/address/wdata | M2的apb写口 | 处理核必须读到APB真正写入的数据 |
| 软件读报文 | M1的re/address，M2的apb_rd_data | M2读口、M1读返回选择 | 必须保留SETUP预取，才能PREADY恒1 |
| 算法取数据 | M3的读使能/索引，M2的proc_rd_data | M2独立读口、M3数据输入 | APB读不能覆盖处理核读地址 |
| 软件启动/配置 | M1的start/mode/mask/exp_len | M3对应输入 | START是命令脉冲，不是长期使能 |
| 软件观察结果 | M3的busy/done/结果/错误 | M1只读状态输入 | 不能在M1伪造结果或另打一拍done |
| 同一时钟域 | 顶层PCLK/PRESETn | 三个模块 | 同步存储返回和状态更新必须有共同边沿 |

### 4. 落到RTL后怎样用人话解释

[ppa_top.sv](ppa_top.sv)只是建立以上连接。比如`.proc_rd_addr(proc_addr)`左边是M2的输入端口，右边是顶层内部信号；该信号由M3的mem_rd_addr_o输出端口驱动。它不是task调用，也不是TB生成的数据。

[tb_lab3.sv](tb_lab3.sv)中`.PSEL(bus.PSEL)`左侧是DUT顶层输入端口，右侧是接口实例bus内部的信号；driver经virtual interface改变bus.PSEL，DUT接收。反向的`.PRDATA(bus.PRDATA)`由DUT输出，driver/monitor读取。接口的PCLK输入端口连接TB时钟PCLK。

bus.busy/done等额外观察线由DUT单向连接到接口，TB没有给这些结果赋值，也没有增加硬件顶层端口。

## 二、验证者：从需求和实现中找出值得怀疑的位置

| 为什么测/怀疑什么 | 怎样触发 | 期望依据与实际检查 | 怎样证明没有空测 |
| --- | --- | --- | --- |
| M1→M2→M3或M3→M1连错 | APB装入8B/type02，启动并轮询 | 输入重建的字节模型与真实M3结果、APB RES读值分别比较 | 接受start数、完成数、driver帧数与测试提交数相等 |
| 第二帧仍返回第一帧结果 | 同一次仿真依次提交8B和13B | 新start时结果清零；两个不同长度均正确 | 检查实际两次start/done，不只是生成两份packet |
| STATUS没有跟随真实状态 | 处理早期和完成后读STATUS | ACCESS沿前busy/done对应01/10 | 记录busy_reads、done_reads，必做测试两者必须非0 |
| busy保护报错但仍写入 | 32B处理中写word7 | PSLVERR=1，读取word7仍等于原值，整帧摘要不变 | scoreboard按ACCESS沿前真实busy统计busy_rejects |
| IRQ没保存或W1C误清另一位 | 正常/错误完成，写0、分位写1 | 依据done新事件和软件EN计算pending，逐拍比较irq；APB读IRQ_STA也比较 | 事件来自真实M3，不是stub；持续done不能清后重触发 |
| 字节尾部和8位溢出算错 | 7B/13B不同payload模式 | 只累计有效payload，A5填充不参与；sum仅留8位 | sum和XOR各自比较，不以格式正确代替摘要检查 |

### 一帧的实际调度顺序

1. generator创建packet，配置或randomize；随机化失败立即fatal，然后经requests mailbox交给driver。
2. driver调用接口transfer；第一个下降沿驱动SETUP，第二个下降沿驱动ACCESS。
3. ACCESS上升沿，DUT接收合法写；monitor在NBA前记录这笔请求与返回值，SRAM模型账本只接受真实成功写入。
4. CTRL.START写沿后，M1产生一拍start；下一上升沿M3接收start，进入PROCESS并清旧结果。scoreboard从已经观察到的报文与配置计算期望。
5. 每个后续上升沿，M2/M3按同步读规则推进；monitor等本沿NBA后1ns再记录新busy/done及结果，发送observed mailbox。
6. scoreboard收到完成观察后比较len/type/sum/XOR/错误；driver继续通过APB轮询和读结果，scoreboard再核对真实APB返回。
7. 最后一笔访问完成后停止monitor；monitor发送结束标记，scoreboard消费完队列才退出。检查帧数、无未完成报文、两个mailbox均空后，TB才置test_done。

simulator是执行这些进程与调度规则的Questa程序，不是其中一个顺序执行的“激励模块”。driver、DUT、monitor、checker是并行的职责。

## 三、§11.4语法如何真正参与验证

| 语法/方法 | 实际用途 | 关键选择 |
| --- | --- | --- |
| rand/constraint/randomize with | packet_item限定合法长度/类型/payload大小；random_test生成12帧 | 检查返回值；负向用例明确关闭三项合法约束，再用内联约束指定三错包 |
| std::randomize with | 帧间空闲0–3周期 | 仅改变合法帧间间隔，不随意改变APB两阶段协议 |
| $urandom、seed | CSR代表性位模式、命令行-sv_seed | 简单随机给一个数；类约束还保证字段关系，不能以循环次数冒充覆盖充分 |
| fork...join | generator和driver有限任务并发，二者都须结束 | 有界requests mailbox形成反压，不丢事务 |
| fork...join_any | 完成轮询和80周期超时竞争 | 放在独立子进程中disable fork，只清理本次超时竞争 |
| fork...join_none、wait fork | 启动monitor/scoreboard后台任务，最终回收 | 先结束driver，再请求monitor停止、发送null、等待scoreboard排空 |
| mailbox | packet传递与实际观察传递 | 传数据需要队列，故不只用可能丢通知的瞬时event；只有一个APB driver，不为无竞争资源添加semaphore |
| extends、virtual | base_test句柄调用派生build_packets | 每个测试只换场景，复用同一驱动、监视、参考与检查路径 |

Lab2的报文格式、按字节摘要和公共类思想得到复用；Lab3新增APB接受时刻、完整存储链路、总线STATUS/RES/IRQ、并发结束对账与受约束随机。不通过复制另一套环境实现新测试。
