# Lab4 设计者与验证者：功能覆盖闭环

## 1. 先看课程目标和分工

本 Lab 选择官方 SV 分支。已有 Lab1–3 RTL 与 Lab3 仿真环境是被验证对象和复用基础；Lab4 的重点不是再写一份 DUT 或参考模型，而是用功能覆盖回答“哪些规格场景确实发生过”，并由 DUT 代码覆盖报告回答“哪些实现结构确实执行过”。设计者关注实现是否符合规格；验证者把规格整理为场景、检查点和覆盖目标，再用缺口指导少量补测。

所以这里保留一个共享的 `ppa_top`、interface、driver、monitor、scoreboard 和参考计算路径。`coverage_test` 只替换场景生成，事务仍须穿过真实 APB/DUT/monitor/scoreboard。观察信号由 TB/interface 接收 DUT 的结果，不是 TB 代替 DUT 驱动结果。

## 2. 为什么覆盖只在检查之后采样

实际顺序可概括为：

1. 测试类创建 `packet_item` 并提交；driver 从 mailbox 取出后，经 APB 写配置/数据并启动处理。
2. monitor 记录真实 ACCESS、响应，以及 DUT 实际完成状态与结果。scoreboard 用已观察输入形成期望，并比较 DUT 输出、APB 读回、IRQ 等。
3. 只有 scoreboard 检查通过，才调用 `sample_access` 或 `sample_frame`。覆盖分类器从已检查的 observation 提取长度、类型、结果等分类，再调用 covergroup 的 `sample()`。
4. testcase 结束时检查事务没有丢失或遗留，再由 coverage collector 报告样本数、各 coverpoint/cross 覆盖率和未满项。

因此，“产生过一个 packet”不等于覆盖命中；被丢弃、未驱动、未完成、scoreboard 失败的场景不能充当通过证据。若真实输入显示帧序号断档或 DUT 结果与检查模型不一致，首先是验证失败，而不是再想办法把对应覆盖数字补满。

## 3. `frame_cg`：一笔已核对帧包含哪些规格属性

每次通过检查的实际帧采一次样。下表中的 bin 名称对应 `lab4_pkg.sv` 中的实现。

| coverpoint | 要回答的问题 | 关键 bins / 目的 |
| --- | --- | --- |
| `cp_length` | 帧长度在规格边界的哪一侧？ | `below4`、`min4`、`middle`、`max32`、`above32`；区分边界与范围内帧 |
| `cp_kind` | 类型是四类支持值之一，还是非法值？ | `type_01/02/04/08` 与显式 `invalid` bin；不是把非法类型默认为未计数值 |
| `cp_mode` | 是否执行 checksum 校验？ | `checksum_enabled` / `checksum_bypassed` |
| `cp_mask`、`cp_permission` | 配置形态如何，当前类型获准还是被拒绝？ | 全开、全关、部分 mask；非法类型、合法且允许、合法但被 mask 拒绝 |
| `cp_expected_length` | expected length 未配置、相符还是不符？ | `not_configured`、`matches_packet`、`differs_from_packet` |
| `cp_irq_enable` | 完成/错误 IRQ 的 EN 组合是否都经历？ | `00/01/10/11` 四种组合 |
| `cp_outcome`、`cp_error_combination` | DUT 最终通过或报错？具体错误是单项还是多项？ | pass/error；无错、单独 length/type/checksum 错、多错 |
| `cp_sequence` | 是否验证首帧以及紧邻的后续帧？ | `first_frame`、`consecutive_frame` |
| `length_by_outcome` | 长度边界分别得到什么结果？ | 长度类别 × pass/error，用来检查长度与结果的组合，而非全字段大笛卡尔积 |

`length_by_outcome` 有两个明确不可达组合：`below4/pass` 和 `above32/pass`。规格要求越界长度报错，故以 `ignore_bins` 排除，不应为了覆盖率伪造正常通过。其余组合包括最小合法长度通过/报错和最大合法长度通过/报错，能检查边界两侧行为。

## 4. `access_cg`：总线访问是否覆盖了关键控制路径

每次通过 scoreboard 检查的真实 APB ACCESS 采一次样。地址按 DUT 可观察区域分类，配合方向和响应，避免把寄存器访问与 packet memory 混为一谈。

| coverpoint | 验证问题 | 目标情形 |
| --- | --- | --- |
| `cp_target` | 地址是否访问了关键寄存器、memory 和 other 区域？ | CTRL、CFG、IRQ_EN、IRQ_STA、EXP_LEN、PKT_MEM、结果/状态、other |
| `cp_direction`、`cp_response` | 读写以及接受/拒绝响应是否都实际发生？ | read/write、accepted/rejected |
| `cp_busy_protection` | memory 写保护在 idle 与 busy 时如何响应？ | 非 memory 写、idle memory 写、busy memory 写拒绝 |
| `cp_irq_operation` | EN 与 W1C 的四种位组合是否都写过？ | enable none/done/error/both；clear none/done/error/both |
| `cp_irq_after_clear` | 清除以后 IRQ 状态是否正确变化？ | 不是清除访问、IRQ 已撤销、另一个 IRQ 仍 pending |

BUSY 拒写不能只看一个 error 位：必须确认该 ACCESS 前 DUT 确实 busy，并核对写未生效。`busy_write_accepted_unexpectedly` 是 `illegal_bins`，因为这代表 DUT 违规，不能作为正向覆盖目标。

## 5. `illegal_bins` 和不可达情形不是“补测目标”

- `ignore_bins` 用于有规格依据、无法合法发生的组合；本模型仅忽略长度越界却 pass 的两个 cross 组合，并在报告中说明原因。
- `illegal_bins` 标记不允许出现的观察：错误结果与规格分类不一致、连续帧序号出现 gap、BUSY 时 packet memory 写却被接受。它们不是应命中的覆盖目标；发生时必须由检查路径报错，不能拿来宣称覆盖达标。
- 其余可达但未命中的 bin 是真实缺口，应该先检查 testcase/采样路径，再设计具有明确检查点的最小补测。不得随意扩大 ignore/illegal 集合来提高百分比。

## 6. 为什么有随机和定向两种激励

Lab3 `random_test` 每个 seed 生成一组受约束的合法 packet，主要探索长度、类型、mode、payload 等组合。driver 另外使用 `std::randomize` 在帧间选 0–3 个空闲周期，用来改变帧间隔；它不是 APB 协议随机化，也不能保证特定 coverpoint 命中。

Lab4 的 `coverage_test` 是另一种目的：把决定目标 bin 的字段用 `packet_item.randomize() with {...}` 固定，仍让合法 payload 受原约束随机产生；只在需要长度越界、非法类型或坏 checksum 时关闭相应合法约束。这样场景类别可预测、摘要数据仍不是手写常量，而且每个结果继续由 scoreboard 检查。固定一个方向的目标 bin 并不意味着绕过 DUT 或参考检查。

这组功能定向补测共 14 帧，覆盖长度边界/中间值、四类合法类型与非法类型、校验开关与错误、mask 允许/拒绝、expected length 三种情形、IRQ EN 组合、多错误、连续帧，以及最大长度处理期间的 memory 写保护探测和 W1C 清除。

代码报告另指出：PROCESS/DONE 的两条复位转移未命中、头部保存寄存器高位没有翻转、APB同步读数据存在只升不降的位。`closure_test` 因而只增加4帧完成和1帧复位中止：255B/typeFF与0B检查完整头字段与非法长度；exp=63/mask=0后恢复检查配置快照；存储器读全1再读0检查两个方向的跳变；在DONE复位，再在最后一帧PROCESS中复位。busy用例还在忙时再写CTRL.START，检查它没有额外启动。

复位中止必须单独对账：实际接受数=正常完成数+实际复位中止数，driver声明的中止数必须与monitor/scoreboard观察一致。中止帧不计为已完成帧，也不会采进frame_cg；复位后第一帧由first_after_reset标记，不能冒充未复位的连续帧。这样以有检查的补测解决可达缺口，而不是过滤这些路径。

数量保持有限：随机测试负责探索广度，定向测试负责补实际功能/代码缺口，两者互补而不是互相取代。

## 7. 从 baseline 到 final 的缺口闭环

1. 以同一初始 testcase 集运行 baseline，归档各测试/seed、回归结果、原始覆盖数据库和报告。
2. 分开查看功能覆盖的每个 coverpoint/cross 与 DUT 的 line、branch、condition、FSM、toggle 五类代码覆盖；不要只看一个汇总数。功能覆盖能回答“规格场景有没有测”，代码覆盖能回答“实现结构有没有执行”，两者不是一个指标。
3. 对缺口判断：是没有激励、观察/采样未接通、测试失败，还是规格上不可达？对真实可达缺口补最小且有 scoreboard 检查的场景；不可达项记录规格依据；代码覆盖过滤则记录过滤项及 raw/filtered 差异。
4. 运行 final 对照相同 seed/配置，确认原测试仍通过、新增场景确实被检查并命中预期 bin；归档回归日志、数据库、raw/filtered 报告和每个未达目标的处理理由。

`coverage_collector.report()` 输出的 `frame_cg`、`access_cg` 及其算术均值只是**功能覆盖**概览，不是 line/branch/condition/FSM/toggle 的代码覆盖率。报告中仍有可达缺口时，应如实保留并说明处理计划；正式结果以实际 Questa 报告为准，不在本说明中预判达标或整体回归通过。
